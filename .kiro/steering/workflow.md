## Production deploy

### Триггер и автономность
- Явная просьба пользователя «задеплой», «примени в production» или эквивалентная формулировка считается подтверждением **конкретного** production deploy.
- После такого запроса агент самостоятельно подключается по SSH и выполняет deploy end-to-end: обновление кода, необходимые миграции/генерацию, сборку, перезапуск PM2, health-check и проверку startup-логов. Не перекладывать команды на пользователя, если доступ технически возможен.
- Разрешение на deploy не является бессрочным разрешением на последующие production-операции. Commit и push выполняются только по отдельной явной просьбе.

### Контекст production этого проекта
- SSH target: `mixa@84.54.56.242`
- Локальный ключ: `$env:USERPROFILE\.ssh\id_rsa_gupil`
- Каталог проекта: `/opt/next-shadcn-dashboard-starter`
- Production branch: `main`
- PM2 application: `bonus-app`
- Health endpoint: `http://127.0.0.1:3000/api/health`

Контекст содержит только несекретные пути и идентификаторы. Никогда не сохранять в документации passphrase, содержимое private key или значения `.env`.

### Безопасный порядок действий
1. Проверить локальный commit/branch и убедиться, что деплоится согласованная ревизия.
2. На сервере выполнить `git status --short --branch`; не сбрасывать, не удалять и не перезаписывать server-side изменения или untracked-файлы. При пересечении изменений сохранить их и выбрать неразрушающий способ применения релиза.
3. Не изменять `.env`/`.env.local` автоматически. Если нужны переменные, сообщить пользователю точные имена и после ручной настройки продолжить проверку.
4. Обновлять `main` только fast-forward способом. Не использовать force push, `reset --hard`, `git clean` или автоматический stash.
5. Не запускать несколько production builds параллельно. Перед стартом проверить процессы сборки и использовать один известный PID/лог.
6. На VPS с ограниченной памятью остановить `bonus-app` перед сборкой, очистить `.next` и запускать Webpack build с `NEXT_PHASE=phase-production-build` и `NODE_OPTIONS=--max-old-space-size=1536`.
7. Считать сборку успешной только после завершения процесса с code `0` и появления непустого `.next/BUILD_ID`. Только после этого выполнять `pm2 restart bonus-app --update-env`.
8. После запуска проверить `pm2 status`, `/api/health` и startup-логи приложения, включая инициализацию Telegram/MAX/очередей, если они затронуты релизом.

### Fallback, если remote Git недоступен
- Создать локальный минимальный `git bundle` только с нужным commit и отсутствующим на сервере диапазоном истории.
- Передать bundle через `scp` с тем же SSH-ключом.
- На сервере выполнить `git fetch <bundle> <ref>` и применить результат через `git merge --ff-only FETCH_HEAD`.
- После успешной проверки удалить временный bundle локально и на сервере.
- Bundle не должен содержать `.env`, private keys, дампы БД или незакоммиченные файлы.

### Безопасный SSH quoting
- Не помещать `|`, `$()`, heredoc и сложные shell-конструкции внутрь незащищённой интерполируемой SSH-строки: часть команды может выполниться локально или породить второй build.
- Для короткой команды использовать PowerShell single-quoted строку `$remote`; для сложного сценария передавать временный shell script через `ssh ... 'bash -s'`.
- Перед остановкой зависшей/лишней сборки определить конкретные PID и завершать только их; не использовать широкие `pkill node`/`killall`, способные остановить PM2 или другие сервисы.
